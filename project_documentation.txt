AUTONOMOUS AGENT DOCUMENT SERVICE
PROJECT DOCUMENTATION

OVERVIEW
This service is an autonomous document generation backend written in Python 3.11 with FastAPI. It receives natural language business requests, dynamically plans a structured document hierarchy, executes drafting tasks sequentially across text and table generation tools, reviews the assembled sections, and compiles a Microsoft Word (.docx) document available for download.

The service is built without LangChain or LangGraph. All orchestration, state tracking, schema validation, and retry logic are implemented in plain, maintainable Python using Pydantic v2 and HTTPX. A single-page demo user interface is provided at the root route for direct browser interaction.


SETUP AND RUN

1. Prerequisites
- Python 3.11 installed on the host system.
- An active Groq API key (primary provider).
- An active Google Gemini API key (fallback provider).

2. Virtual Environment Setup
Create and activate a virtual environment:
  python -m venv .venv
  .venv\Scripts\activate   (Windows PowerShell: .venv\Scripts\Activate.ps1)
  source .venv/bin/activate (Linux / macOS)

3. Install Dependencies
  pip install -r requirements.txt

4. Configure Environment Variables
Copy the template to create .env:
  copy .env.example .env
Edit .env and populate:
  GROQ_API_KEY=your_groq_api_key
  GEMINI_API_KEY=your_gemini_api_key
  FORCE_FALLBACK=false
  GROQ_MODEL=llama-3.3-70b-versatile
  GEMINI_MODEL=gemini-2.5-flash

5. Run the Server
Launch the server using uvicorn:
  uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

6. Access the Application
- Demo Web UI: http://localhost:8000/
- Interactive Swagger API Documentation: http://localhost:8000/docs

7. Run the Test Suite
Run the automated test suite with pytest:
  pytest -v

8. Code Quality and Linting
Run Ruff check across codebase:
  ruff check app tests scripts

9. Provider Connectivity Check
Run the diagnostic script to verify Groq and Gemini API status without exposing keys:
  python scripts/check_llm.py


ARCHITECTURE AND FILE RESPONSIBILITIES

app/main.py
Defines the FastAPI application and HTTP routes (GET /, GET /page, POST /agent, GET /download/{run_id}, GET /health, GET /favicon.ico). Houses request validation logic rejecting empty requests, inputs under 10 or over 2000 characters, and obvious prompt-injection attempts. Catches PlanningError (returning HTTP 422), LLMProviderError (returning HTTP 502), and sets httpx/httpcore loggers to WARNING to prevent logging API tokens or endpoints.

app/agent.py
Coordinates the multi-stage document lifecycle:
- PlanningError: explicit exception raised when planning fails validation after retries.
- Planner: produces document metadata, assumptions, and 5 to 9 tasks. Enforces table generation for plans/proposals with automated fallback conversion for missing tables.
- Executor: initializes all planned tasks with status "pending", transitions them to "running" prior to dispatch, and executes them with a two-tier recovery mechanism: a 5-second immediate retry on task failure followed by an extra recovery pass over all failed tasks.
- Rolling Context: maintains a rolling context capped at the last 3 section snippets of at most 120 characters each.
- Reviewer: analyzes assembled sections and triggers an optional single revision pass on flagged sections. If reviewer calls fail, it returns an honest skipped review message.
- Summary generator: synthesizes a concise executive summary; if the call fails, it derives an honest fallback from real data indicating exactly how many sections completed out of the total.
- Response compiler: computes the "complete" boolean flag (true only if every planned task has status "done").

app/llm.py
Lightweight async LLM client connecting to Groq (via OpenAI-compatible endpoint) and Gemini (via REST endpoint). Uses a unified _post_with_retry helper with 3 retries. Dynamically reads the Retry-After header on HTTP 429 (capped at 30s) or applies exponential backoff starting at 3s (3, 6, 12) for 429/5xx/timeouts. On terminal provider failure, logs the HTTP status code and first 200 characters of the response body without exposing URLs or keys. Incorporates an asyncio.Semaphore(1) and a minimum gap of 1.5 seconds between Groq calls (LLM_MIN_GAP_SECONDS) to prevent rate-limit bursts. Passes API credentials via standard headers (Bearer token for Groq, x-goog-api-key for Gemini).

app/schemas.py
Pydantic v2 models defining all input/output contracts: document types, task models, section content, table content, review outputs, and API responses (including the "complete" boolean indicator).

app/tools.py
Implements the write_section and make_table tools. Enforces strict size bounds in prompts: each section is constrained to 2 short paragraphs and at most 5 bullets; each table is constrained to at most 6 rows. Validates model outputs against Pydantic models with one retry on failure.

app/docx_builder.py
Constructs publication-grade Word (.docx) files using python-docx. Applies 1-inch margins, Calibri 11pt styling, a custom title block, an Assumptions section, properly formatted headings, bullet lists, styled table headers with background shading, and dynamic page numbering in the footer. Accepts a configurable output directory.

app/store.py
A thread-safe in-memory store protected by a re-entrant lock. Stores run records including metadata, execution status, review results, and file paths.

scripts/check_llm.py
Standalone verification script sending a minimal probe ("Reply with the word ok") to Groq and Gemini independently. Prints HTTP status code, provider name, and first 100 characters of output or error without leaking credentials.

static/index.html
Single-page web demo UI with vanilla JavaScript and CSS (no libraries, frameworks, or build steps). Provides example buttons, character count, live generation spinner, structured section outputs, and direct document download.

outputs/
Directory where generated .docx files are saved, named by run_id. Contains .gitkeep to persist directory tracking while ignoring generated documents in git.

tests/test_requests.py
Pytest suite covering input bounds, prompt injection blocking, JSON parsing, docx layout, retry and fallback mechanisms, 422 planning failure handling, 502 upstream errors, reviewer skipping honesty, and end-to-end execution writing to isolated temporary directories.


AGENT WORKFLOW

Stage 1: Input Validation (main.py)
The incoming request is sanitized and checked against strict bounds. If the text is empty, shorter than 10 characters, longer than 2000 characters, or contains adversarial phrases such as "ignore previous instructions", an HTTP 400 error is immediately returned with a descriptive error message.

Stage 2: Dynamic Planning and Table Enforcement (agent.py)
The planner prompts the LLM to inspect the request and determine:
- The appropriate document type from seven supported options (proposal, meeting_minutes, project_plan, business_report, technical_design, sop, product_spec).
- A descriptive title.
- Explicit assumptions that resolve missing information, ambiguity, or conflicting instructions.
- A sequential task list containing between 5 and 9 tasks with assigned tools (write_section or make_table).
- Rule: For project_plan and proposal documents, the planner prompt instructs the model to include at least one make_table task for timelines or budgets.
- Automated Post-Check: If the model returns a project_plan or proposal without any make_table tool, the orchestrator logs a warning and automatically converts the first task whose title contains "timeline", "schedule", "budget", or "risk" to make_table.
If planning fails validation after retries, a PlanningError is raised, causing the API to return HTTP 422.

Stage 3: Task Status Tracking and Execution (agent.py and tools.py)
Tasks are executed sequentially:
- Initialization: A TaskResult object is pre-created for every planned task with status "pending".
- Transition: Immediately before invoking the tool, the task status is updated to "running".
- Dispatch: A tool dictionary routes the task to write_section or make_table, maintaining a rolling context of the last 3 section snippets capped at 120 characters each.
- Token Economy: Prompts instruct the model to produce concise sections (2 short paragraphs, at most 5 bullets) and compact tables (at most 6 rows), cutting token consumption per call.
- Task-Level Recovery: If a task fails after its internal schema retries, the system pauses 5 seconds and tries that task one more time before marking it failed.
- Recovery Pass: After all tasks complete, if any tasks remain in a "failed" status, the orchestrator executes a dedicated second pass over just those failed tasks. Only then are persistent failures marked failed for good.
- Completion: Upon successful execution, the task status transitions to "done". If an unrecoverable failure occurs, it transitions to "failed" and notes the failure reason in the document. No task remains in "pending" or "running" state.

Stage 4: Document Review and Revision (agent.py)
Once all sections are assembled, the reviewer inspects the full document text against the user request and recorded assumptions. If the review model call or its parsing fails, the agent honestly sets the review summary to "Review skipped because the reviewer call failed." and proceeds without fabricating a success assessment. If critical issues are genuinely flagged, the orchestrator executes at most one revision pass on flagged sections.

Stage 5: Word Document Compilation (docx_builder.py)
The final document is rendered into a .docx file:
- Margins: 1 inch (top, bottom, left, right).
- Font: Calibri 11pt, 1.15 line spacing.
- Header/Title Block: Large document title, uppercase document type, and generation date.
- Assumptions Section: Heading and bulleted list detailing all assumptions and resolved conflicts.
- Section Headings: Consistent Calibri Heading 1 styles.
- Tables: Center-aligned, Table Grid border, dark slate header background (#1F4E79) with bold white text.
- Footer: Right-aligned dynamic page numbers (Page X).
The file is saved to outputs/{run_id}.docx (or a configurable test directory).

Stage 6: API Response (main.py)
The endpoint returns JSON containing run_id, doc_type, title, summary, assumptions, per-task statuses, review findings, list of LLM providers utilized, download URL, and a boolean "complete" flag indicating whether all planned tasks completed successfully.


RETRY AND FALLBACK DESIGN AND REASONING

1. Merged Retry Helper (_post_with_retry)
Both Groq and Gemini calls route through a single async helper _post_with_retry. The helper executes HTTP requests using HTTPX with a 45-second timeout and up to 3 retries.
- On HTTP 429: Checks the Retry-After response header (in seconds). If present, waits that exact duration, capped at 30 seconds.
- Missing Header or 5xx/Timeouts: Applies exponential backoff starting at 3.0s (3s, 6s, 12s).
- Terminal Failure Logging: When retries are exhausted or a non-retriable status occurs, logs the HTTP status code and the first 200 characters of the response body to clarify the root cause without logging keys or URLs.

2. Pacing and Concurrency Protection
To prevent bursts of rapid sequential requests from tripping Groq per-minute rate limits, LLMClient implements an asyncio.Semaphore(1) and enforces a minimum gap of 1.5 seconds between Groq calls (configurable via LLM_MIN_GAP_SECONDS).

3. Primary Provider: Groq
Groq provides high-speed inference using llama-3.3-70b-versatile (or a model configured via GROQ_MODEL) through its OpenAI-compatible completions endpoint. Bearer token authorization is sent in the Authorization request header.

4. Fallback Provider: Google Gemini
If Groq exhausts its retries, is rate-limited, or encounters non-recoverable errors (such as 401, 404, or network outage), the client logs a warning and switches to the Google Generative Language REST endpoint (gemini-2.5-flash). Credentials are transmitted strictly via the x-goog-api-key header, never exposed in URL query parameters.

5. Force Fallback Toggle
An environment variable FORCE_FALLBACK (boolean) allows developers or evaluators to bypass Groq entirely and route all traffic to Gemini. This enables verifiable testing of the fallback system on demand without simulating an actual Groq outage.

6. Provider Accounting
Every invocation returns the name of the provider that produced the output ("groq" or "gemini"). The agent orchestrator aggregates these names into a sorted list returned in the API response under providers_used.

7. Terminal Failure Handling
If both Groq and Gemini fail to produce a valid response, the client raises LLMProviderError. The FastAPI route catches this exception and returns an HTTP 502 Bad Gateway response with clear diagnostic details.


DEMO WEB USER INTERFACE

DEBUGGING STORY: GROQ FREE-TIER 429 AND RECOVERY

Problem:
During initial evaluation of the complex board request, an execution run concluded with 3 of 6 tasks failing and providers_used = ["groq", "system"]. Groq's free-tier rate limits returned HTTP 429 responses under rapid sequential calls. The existing retry logic waited only 1s and 2s before giving up, while the Gemini fallback simultaneously encountered quota exhaustion (HTTP 429), leaving the generated Word document incomplete.

Root Causes:
1. No Call Pacing: Sequential task loops dispatched LLM calls milliseconds apart, exceeding Groq's per-minute request rate.
2. Short Retry Windows: Fixed 1s and 2s backoffs were too short for Groq's 429 rate-limit bucket to replenish.
3. Ignored Retry-After Guidance: Provider-specified wait times in HTTP headers were neglected.
4. Verbose Prompt/Output Payloads: Unconstrained section prompts and outputs inflated token consumption.
5. Immediate Task Abandonment: A single failure in a tool call immediately marked the section failed with no second chance.

Solution & Implementation:
1. Dynamic Rate-Limit Handling: Configured _post_with_retry to parse Retry-After headers (capped at 30s) and fallback to exponential backoff starting at 3s (3, 6, 12) with max_retries = 3. Logged HTTP status code and response body prefix (200 chars) on terminal errors.
2. Call Pacing: Added asyncio.Semaphore(1) and enforced a configurable minimum delay of 1.5s between Groq calls via LLM_MIN_GAP_SECONDS.
3. Prompt Token Bounds: Constrained sections to 2 short paragraphs and <= 5 bullets, tables to <= 6 rows, and rolling context to the last 3 snippets of <= 120 characters each.
4. Two-Tier Task Recovery: Added an immediate 5-second backoff retry for failed tasks, followed by a dedicated recovery pass over all failed tasks after the primary loop.
5. Honest Reporting: Added a boolean "complete" flag to AgentResponse, an honest summary fallback derived from completed section counts, and an amber warning alert in the web UI.

TRADEOFF: AUTONOMOUS PLANNING VS DETERMINISTIC WORKFLOW

A deterministic workflow uses hardcoded templates or rigid finite state machines for document drafting. For example, a project plan would always produce the same five fixed sections: Introduction, Timeline, Data, Training, and Risks. This guarantees predictable execution times, lower token usage, and zero variance in document structure. However, deterministic workflows fail when business requests vary widely. A board review with no budget numbers or an SOP for data access cannot fit into a static migration template.

Autonomous planning gives the agent freedom to inspect the prompt, select the document type, define between 5 and 9 tasks tailored to the specific problem, and decide which sections require narrative prose versus tabular data. The risk of autonomous planning is non-determinism: an LLM could generate too few tasks, duplicate sections, or hallucinate irrelevant steps.

To balance flexibility and reliability, this service constrains the planner using a strict Pydantic schema:
- doc_type is constrained to an enum of seven allowed business formats.
- The task list is enforced to have a minimum length of 5 and maximum length of 9.
- Each task requires an assigned tool from a closed set (write_section or make_table).
- The model is instructed to capture missing data in an explicit assumptions list.
- A built-in validation retry feeds schema errors back to the model if it violates these boundaries.
- A deterministic post-check verifies that project plans and proposals always include a make_table task.
This approach provides the structural adaptability of autonomous planning while maintaining the predictability and validation guarantees required in production backend systems.


KNOWN LIMITATIONS

1. In-Memory Store
Run records are stored in RAM. A service restart or worker recycling wipes the run history and download lookups.

2. Sequential Execution Latency
Document tasks are processed sequentially to maintain narrative context across sections. A document with 8 sections requires 10 to 12 serial LLM calls (plan, 8 sections, review, optional revision, summary), resulting in execution times between 15 and 30 seconds depending on API response latency.

3. Single Process Scope
The service runs as a single FastAPI instance without background worker coordination. Long-running requests hold the HTTP connection open until completion.

4. Keyword-Based Prompt-Injection Filter
The prompt-injection defense uses a substring blacklist (such as "system prompt", "ignore previous instructions", "developer mode"). While this blocks standard adversarial attempts without LLM overhead, it can produce false positives on legitimate technical requests that mention phrases like "system prompt" in an educational or documentation context.


NEXT STEPS FOR SCALE

1. Distributed Task Queue
Decouple request ingestion from document generation using Celery, ARQ, or Redis Streams. POST /agent would validate input, enqueue a job, and return a 202 Accepted status with a job_id. Clients would poll a GET /agent/{job_id} endpoint or listen to WebSocket / webhook notifications.

2. Persistent Storage
Replace RunStore with PostgreSQL or MySQL using SQLAlchemy for transactional record storage. Save generated .docx binaries to an S3-compatible object store (such as Amazon S3, Google Cloud Storage, or MinIO) with time-limited pre-signed URLs for downloads.

3. Parallel Execution of Independent Sections
Analyze dependencies among planned tasks during the planning phase. Sections that do not rely on preceding sections (e.g., Risk Matrix and Team Training) can execute concurrently using asyncio.gather, reducing total generation latency by 40% to 60%.
